## 1. What We Are Doing

This week you learn to use motion for a reason. You audit real products, choose timing and easing, build transitions, and write a spec an engineer can build. You also make a reduced-motion version and delete animation that does nothing.

Task groups:
- Group 1: Audit and decide. I2.1, I2.2, I2.3.
- Group 2: Build and specify motion. I2.4, I2.5, C11.1. Plus critique.
- Group 3: Orientation and principles. I2.6, P10.1.
- Group 4: System, fundamentals and lab. S12, F10, L-PR2.
- Group 5: Code corner. Z10.1.

## 2. Why We Are Doing It

In a real product team in India, motion is often the difference between a payment flow that feels clear and a form that feels broken. A working product designer must explain why a transition is 200ms, not 400ms, and must make it safe for people with motion sensitivity. This week also matters for your portfolio. A motion spec with tokens, a reduced-motion variant, and a clear purpose test is rare work. It shows craft, systems thinking, and accessibility in one place.

## 3. What to Learn First

By the end of the week you can:
- Choose a duration and an easing curve for a reason you can state.
- Justify every animation by what it communicates, and delete the ones that communicate nothing.
- Build a reduced-motion alternative that keeps all information clear, with less motion or with static cues.
- Specify motion precisely enough for an engineer to build it.

Core ideas to review first:
- Animation has five legitimate jobs: show where something came from, show what changed, keep a user oriented during a layout change, indicate progress, and direct attention to something that just appeared.
- Entry uses ease-out. Exit uses ease-in. Movement within the screen uses ease-in-out. Linear is only for constant rate, like a progress bar or spinner.
- Duration bands: 100-150ms for small state changes on a control, 200-300ms for entering and exiting elements, 300-400ms for a full-screen or layout transition. Above 400ms needs a written reason.
- Reduced motion does not mean the animation is simply removed, and it does not mean no motion. It means no large-area movement, no parallax, no scaling of big elements, no spinning. A cross-fade is usually acceptable. Animation may be disabled if the final state and all information remain clear through text, layout, or other static cues.
- Motion tokens stop every designer from inventing a new duration.
- Inconsistent direction is worse than no motion.

#### Task - Motion audit (ID `I2.1`)

##### 1. What We Are Doing
Audit motion in three real products. For each transition, say what it communicates, how long it takes, and whether you would keep it.

##### 2. Why We Are Doing It
You need evidence before you design. Most people see motion as "nice". This task trains you to see it as information or decoration.

##### 3. What to Learn First
The five roles of UI animation from Day 1. The cost of decoration on a billing screen. Public pages only: no login screens, no personal data in your captures.

##### 4. Where to Find Resources
Use the Day 1 row: Designing Interface Animation Ch. 1-3, Material 3 motion overview and transition patterns, Apple HIG Motion.

##### 5. Step-by-Step Guide
1. Use public pages or public demo screens only. Never record personal profiles, names, faces, phone numbers, IDs, balances, or real transactions. If a screen sits behind a login, leave it.
2. Pick three real products you use. One should be a payment or banking app, where motion is usually conservative for good reasons.
3. Capture five transitions in each product. A short sequence of 3 to 5 screenshots per transition is enough. You do not have to record video.
4. Screenshots on Mac: press Shift + Command + 4 and drag the area, or press Shift + Command + 4 then Space to capture one window.
5. Screenshots on Windows: press Windows key + Shift + S and drag the area. The snip goes to the clipboard, so paste it into a document and save it.
6. If you prefer video: on Mac, press Shift + Command + 5 to record the screen. On Windows, press Windows key + G to open the Game Bar and record. Videos stay out of Git. Only frames go in.
7. For each transition, identify: what it communicates, roughly how long it takes, whether it helps or delays, and whether you would keep it.
8. Find one animation in each product that exists purely as decoration. Say what removing it would cost.
9. Find one that genuinely helps. Say what removing it would cost.
10. Save the notes and your frame sequences in your week 10 folder.

Worked example:
> App: A payments app, the "send money" confirmation.
> What it communicates: the amount card lifts and moves toward the recipient's avatar. This shows the direction of the transfer and which account it went to. About 400ms.
> Helps or delays: helps. It answers "did it go to the right person" without the user reading anything.
> Would I keep it: yes, but I would shorten it to 300ms. At 400ms it is noticeable on repeat use, and this is a repeated action.

If you get stuck: watch one transition frame by frame. Read the Day 1 chapter on the five roles again. Ask in Discord with a short clip and your note.

How to think about it: ask what the user knows after the animation that they did not know before.

#### Task - Duration and easing decisions (ID `I2.2`)

##### 1. What We Are Doing
List every animation in your flow. Give each one a duration and an easing curve, with a reason.

##### 2. Why We Are Doing It
An engineer cannot build "make it smooth". Duration and easing are the build values.

##### 3. What to Learn First
The duration bands and the easing rule from Day 2. Linear is only for constant rate.

##### 4. Where to Find Resources
Use the Day 2 row: Designing Interface Animation timing and easing chapters, easings.net, Material 3 "Easing and duration".

##### 5. Step-by-Step Guide
1. List every animation you intend to have in your flow.
2. For each, assign a duration. Use the bands: 100-150ms for small state changes on a control, 200-300ms for entering and exiting elements, 300-400ms for a full-screen or layout transition, above 400ms only with a written justification.
3. For each, assign an easing curve and state why that curve for that motion.
4. Anything above 400ms needs a specific reason. "It looks nicer" is not one.

Worked example:

| Animation | Duration | Easing | Why |
|---|---|---|---|
| Button pressed state | 100ms | ease-out | Must feel immediate. Any longer and the button feels unresponsive. |
| Cancellation confirmation dialog entering | 250ms | ease-out | Enters quickly and settles. Long enough to see where it came from. |
| Plan comparison expanding | 300ms | ease-in-out | The layout is changing height, and the user needs to track what moved. |
| Progress bar during payment | continuous | linear | It represents actual elapsed progress. Easing would misrepresent the rate. |

If you get stuck: start with the button, the dialog, and the progress bar. Ask in Discord with your table and the reason you are unsure about.

##### 6. What to Commit
- [ ] File: `students/UX{n}/week10/I2-2-timing.md`
- [ ] Every animation listed
- [ ] Duration assigned within the bands, or justified above them
- [ ] Easing assigned with a reason per animation
- [ ] Linear used only where the motion genuinely has constant rate
- [ ] Commit message: `I2.2 timing decisions`

#### Task - Reduced motion (ID `I2.5`)

##### 1. What We Are Doing
Define a reduced-motion alternative for every animation. Check if information is lost and say how you compensate.

##### 2. Why We Are Doing It
For some people, large-area motion and parallax cause genuine nausea and dizziness. This is not a preference. It is a requirement.

##### 3. What to Learn First
`prefers-reduced-motion` exists for motion sensitivity. Reduced motion does not mean no motion, and it does not mean the animation is simply removed. A cross-fade is usually acceptable. Animation may be disabled if the final state and all information remain clear through text, layout, or other static cues.

##### 4. Where to Find Resources
Use the Day 4 row: WCAG 2.3.3, WCAG 2.2.2, A List Apart "Designing Safer Web Animation For Motion Sensitivity".

##### 5. Step-by-Step Guide
1. For every animation, define the reduced-motion alternative.
2. Reduced motion does not mean no motion. It means no large-area movement, no parallax, no scaling of big elements, no spinning. A cross-fade is usually acceptable. Animation may be disabled if the final state and all information remain clear through text, layout, or other static cues.
3. For each, state whether reduced motion loses any information. If it does, say how you compensate, usually with text or a layout cue.
4. Check that nothing in the flow communicates solely through motion. Motion must be a reinforcement, never the only channel.

Worked example:

| Animation | Full motion | Reduced motion | Information lost? |
|---|---|---|---|
| Dialog entering | Scales from 95% and slides up 12px, 250ms ease-out | Opacity 0 to 1, 150ms | No. The dialog's presence is the information, and the fade still conveys arrival. |
| Plan card expanding | Height animates, contents stagger in, 300ms | Height changes instantly, contents fade in 100ms | Slight. Compensated by keeping the expanded card's border highlighted for 1s. |
| Success checkmark drawing | Path draws over 400ms | Checkmark appears at full opacity with the text | No. The text "Payment received" carries the meaning. |

If you get stuck: pick the biggest movement first. Search "prefers-reduced-motion safe animation". Ask in Discord with the animation clip and your alternative.

How to think about it: ask what the user must still know when the movement is gone.

- [ ] Information loss assessed per animation, with compensation where needed
- [ ] Nothing in the flow communicates solely through motion
- [ ] Commit message: `I2.5 reduced motion`

#### Task - Motion spec (ID `C11.1`)

##### 1. What We Are Doing
Write the spec an engineer would implement from. Include motion tokens, exact values, and the reduced-motion variant in the same spec.

##### 2. Why We Are Doing It
"Make it smooth" is not a spec. Tokens and exact values make the motion system buildable and consistent.

##### 3. What to Learn First
The seven attributes: property, from value, to value, duration, easing, delay, trigger. Plus the reduced-motion variant. Use cubic-bezier or token names, not adjectives.

##### 4. Where to Find Resources
Use I2.2 for timing and I2.5 for reduced motion. Define initial token names in this task; reuse them in S12. Use the Day 2 Material 3 easing page if you need curve names.

##### 5. Step-by-Step Guide
1. For each animation, write the property that changes.
2. Write the start value and the end value of that property.
3. Write the duration, in milliseconds.
4. Write the easing curve as a cubic-bezier value or a named token. Do not use adjectives.
5. Write any delay, in milliseconds. Write "none" if there is no delay.
6. Write the trigger: what starts the animation (a tap, a screen loading, a value changing).
7. Write the reduced-motion alternative for the same animation.
8. Group repeated values into motion tokens: `duration-fast`, `duration-medium`, `easing-standard`.
9. Use the tokens in the spec. If you have eleven different durations, you do not have a system.
10. Put the reduced-motion variant in the same spec, not in a separate document.

If you get stuck: group your durations by use. Search "motion tokens duration easing". Ask in Discord with your token table and the values you are unsure about.

How to think about it: a token is a shared decision. If two animations use the same value for the same reason, they should use the same token.

##### 6. What to Commit
- [ ] File: `students/UX{n}/week10/C11-1-motion-spec.md`
- [ ] Every animation fully specified with all seven attributes
- [ ] Easing given as cubic-bezier values or named tokens, not as adjectives
- [ ] Motion tokens defined and used
- [ ] Reduced-motion variant included in the same spec, not in a separate document
- [ ] Commit message: `C11.1 motion spec`

#### Task - Orientation and continuity (ID `I2.6`)

##### 1. What We Are Doing
Walk your whole flow as a sequence. Find every place where the user cannot tell where they came from, where they are, or what just changed.

##### 2. Why We Are Doing It
Motion keeps people oriented during layout changes. Continuity is how a flow feels like one place, not a set of jumps.

##### 3. What to Learn First
Shared element transitions, consistent entry directions, and a stable header. State your directional rule and hold it.

##### 4. Where to Find Resources
Use the Day 5 row: About Face on orchestration, flow, and maintaining orientation. Watch your I2.4 recordings in sequence.

##### 5. Step-by-Step Guide
1. Walk your whole flow as a sequence. Ask at each step: does the user know where they came from and where they are?
2. Find every place where something appears with no spatial origin, or where the layout jumps.
3. Fix them using continuity: shared element transitions, consistent entry directions, a stable header.
4. State your directional rule and hold it. If forward is right-to-left, backward is left-to-right, everywhere, with no exceptions. Inconsistent direction is worse than no motion.

If you get stuck: record the flow in one take and watch it without stopping. Search "shared element transition continuity". Ask in Discord with the timestamp where the jump happens.

How to think about it: after each tap, ask three questions: what changed, where did it come from, where am I now?

#### Task - Fundamentals: perception and teardown (ID `F10`)

##### 1. What We Are Doing
Write a why session on perception of time and change blindness. Do a teardown of a UPI payment app's transaction flow for motion and feedback. Continue the drill.

##### 2. Why We Are Doing It
Motion is about how people notice change. The same transition can feel different on first use and on repeated use. This task connects motion to real perception.

##### 3. What to Learn First
Two ideas first, in plain words:
- Perception of time. How long a duration feels depends on the context. Waiting feels long. The same transition can feel fine on first use and slow on the tenth, because the user already knows the outcome.
- Change blindness. People often miss a change on screen when it happens without a visible transition, especially when their attention is somewhere else. Motion is one cue that helps them notice the change.

##### 4. Where to Find Resources
Do a short reading before F10.1. Two options: search https://www.nngroup.com/ for "change blindness" and read one article, or read the perception and memory section in About Face, the book you used on Day 5. Check the source and the date before use. Then use your own experience from the week.

##### 5. Step-by-Step Guide
1. F10.1: Write the why session on perception of time and change blindness. Compare first and repeated use of one transition. Describe a change a user might miss and assess whether motion or a static cue would help. Save it.

#### Task - Button click state (ID `Z10.1`)

##### 1. What We Are Doing
Read a little JavaScript. Make a button click change a state on a page. Commit the `.html` file with one paragraph that explains what each line does.

##### 2. Why We Are Doing It
Designers need to read and edit a little code. A click that changes state is the smallest useful interaction. It helps you talk with engineers and test your own prototypes.

##### 3. What to Learn First
A click event, a function, and one change on the page. You do not need to master programming.

##### 4. Where to Find Resources
Use https://web.dev/learn/javascript and MDN Scripting: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Scripting.

Setup: VS Code section in `../04-Tools-Setup.md`.

##### 5. Step-by-Step Guide
1. Open VS Code. Mac: Applications > Visual Studio Code. Windows: Start menu > Visual Studio Code.
2. In `students/UX{n}/week10/`, create `z10-1-button-state.html`.
3. Add a button and one status line on the page. The status line must change when the button is clicked.
4. Read the start of web.dev/learn/javascript and the MDN Scripting page until you can add a click event.
5. Add a small script. When the button is clicked, change the status text or a CSS class. This is the state change.
6. Open the file in your browser. Mac: double-click the file or drag it into the browser. Windows: double-click the file.
7. Click the button. Check that the visible state changes.
8. Press Tab to reach the button, then press Enter or Space. Check it still works.
9. Write one paragraph as an HTML comment at the top of the file. Explain what each line does.

If you get stuck: search "addEventListener click change textContent". Read the MDN Scripting page on events again. Ask in Discord with a screenshot and the browser console error.

How to think about it: state is the thing that changes. The button only starts the change.
