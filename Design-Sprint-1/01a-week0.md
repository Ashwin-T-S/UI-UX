## 1. What We Are Doing

This week you set up every tool the program uses, and you prove it works. You make your accounts, your Figma file, your code editor, your Git setup, your first commit, and your first pull request. You end with a small web page you built yourself.

The task groups:

- **Group 1 - Accounts and tools:** Z0.1, Z0.2, Z0.3
- **Group 2 - Your first commit and pull request:** Z0.4, Z0.5, Z0.6
- **Group 3 - Your first page and your first accessibility check:** Z0.7, Z0.8

## 2. Why We Are Doing It

A working product designer in India does not only draw screens. You hand work to engineers, you take feedback in a shared repo, and you show evidence. In a real team, the design file and the repo are where work lives. If you cannot get your work into the repo, your work does not exist for the team.

This week is also the week you set the habit for 27 weeks. One task, one commit with all files listed for that task. Small steps, every week. It is boring on purpose. A designer who commits every week for six months has a portfolio. A designer who waits for a perfect week has nothing.

For your portfolio: the repo builds in public. Your later case studies, your code page and your portfolio page all sit in this same place. Learning the path now saves you hours later.

## 3. What to Learn First

By the end of the week you can:

- Log in to GitHub, Figma and Penpot without help.
- Say what the Figma Starter plan allows and why that changes how you save files.
- Open VS Code, and run `git --version` in a terminal on your own computer.
- Fork a repo, clone it, make a branch, commit two files and open a pull request.
- Make one web page with a heading, a paragraph and an image.
- Run two free accessibility tools and write down what they do.

Core ideas to review first, in plain words:

- **Repo:** a shared folder on GitHub, with history.
- **Fork:** your own copy of someone else's repo, on GitHub.
- **Clone:** a copy of a repo on your own computer.
- **Branch:** a safe side path where you work. `main` stays clean.
- **Commit:** one saved change, with a short message.
- **Pull request (PR):** a request to put your branch into `main`. Someone else approves it.
- **Markdown:** plain text with simple symbols, saved as `.md`. It is how you write notes in the repo.
- **Alt text:** the words a screen reader reads when it meets an image.

#### Task - Fork, clone, branch (ID `Z0.4`)

##### 3. What to Learn First

##### 2. Why We Are Doing It
When you upload your work to the shared repo, the team can review it. A designer who keeps everything local gets nothing. Also, the pull request page is where your reviewer writes comments. It is a normal part of the job.

##### 3. What to Learn First

- **Head** is where the work comes from: your branch.
- Only the team leader merges. You open the request and stop.

### Group 3 - Your first page and your first accessibility check

#### Task - Code corner: your first HTML page (ID `Z0.7`)

> **Code corner - about 30 minutes of code.** You only need one page with three things on it: a heading, a paragraph and an image. This is not a programming course.

##### 1. What We Are Doing
You build one small web page on your own computer. It has a heading, a paragraph and an image with real alt text. Then you save a screenshot of it and a note with the code inside.

##### 2. Why We Are Doing It
A working product designer reads a page like an engineer does. When you know that an image sits inside one line of code, alt text stops being a checkbox and becomes a choice you make. Every accessibility fix later in the program becomes easier after this task.

##### 3. What to Learn First
- HTML is the structure of a page. Tags mark the parts.
- `<h1>` is the main heading. `<p>` is a paragraph. `<img>` is an image.
- `alt` is the text a screen reader reads when the image cannot be seen.
- A file named `index.html` is the usual first page of a site.
- A code block in markdown puts code on its own grey box. You open it with three backticks followed by the word `html`, and close it with three backticks on their own line.

##### 4. Where to Find Resources
- MDN Learn web development, Getting started: https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started. Start at the top and stop when you have made one page.
- web.dev Learn HTML: https://web.dev/learn/html. Use it when you want one tag explained again.
- `../04-Tools-Setup.md`, the part on VS Code.
- Search keywords: "html img alt text", "html basic page example", "how to open html file in browser", "markdown code block".

#### Task - Accessibility tools check (ID `Z0.8`)

##### 1. What We Are Doing
You open or install four free accessibility tools and run one check with each of the first two. You write one line on what every tool does.

##### 2. Why We Are Doing It
Accessibility is not a topic you read about once. It is a set of tools you use every sprint. If you install them now, you will actually use them in week 4. If you wait, you will skip the checks when you are busy. The free tools are enough. Do not install a paid tool. If a tool asks for a card, stop.

##### 3. What to Learn First
- A **screen reader** reads the page aloud. VoiceOver is built into Mac. NVDA is free on Windows.
- **Lighthouse** is inside Chrome. It scores a page, including accessibility.
- **axe DevTools** is a browser extension that lists problems on a page. The free tier has limits: check before use.
- **Stark** is a Figma plugin for contrast checks. The free tier has limits: check before use.

##### 4. Where to Find Resources
- `../04-Tools-Setup.md`, the part on accessibility tools.
- NVDA for Windows, free: https://www.nvaccess.org/
- WCAG 2.2 Quick Reference, for the words: https://www.w3.org/WAI/WCAG22/quickref/
- For axe DevTools, WAVE and Stark, links are in `../04-Tools-Setup.md`. Check the free limit before use.
- Search keywords: "download chrome mac", "download chrome windows", "turn on voiceover mac", "nvda screen reader start", "lighthouse accessibility tab chrome", "stark figma contrast checker".
