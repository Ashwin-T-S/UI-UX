## 1. What We Are Doing

This week you design component APIs, not just buttons. A component API is the list of parts and options a component gives to other people. You build six components, document them, set composition rules, and write an accessibility spec.

Task groups:
- T2.1 to T2.6: component APIs, builds, slots, documentation, composition rules, accessibility.
- P14.1: one component ADR.
- S17.1 to S17.3: cohort system work.
- F14.1 to F14.3: why session, teardown, drill.
- L-AI4: read code you did not write.

## 2. Why We Are Doing It

A working product designer in India often joins a team with many buttons that look the same but behave differently. Teams then ask: what does this component support, when should I use it, and why is this the default? Without an API, docs, and rules, people build their own versions.

This week matters for Sprint 4 because your system must work for other designers and engineers, not only for you. It matters for your portfolio because it shows systems thinking, documentation, accessibility, and working with engineers.

## 3. What to Learn First

By the end of the week you can:
- Design a component API and defend every property in it.
- Decide what a component does not do, and say where that thing belongs instead.
- Write documentation a stranger can build from without asking you a question.
- Compose components without creating combinations that should not exist.

Core ideas to review first:
- **Component API:** the parts and settings a component exposes to other people.
- **Variant:** a fundamentally different version of a component.
- **Size:** a supported size step, with a reason for the number.
- **State:** default, hover, focus, active, loading, disabled, and others.
- **Slot:** a place where other content can go.
- **Prop:** a setting on the component, with a default.
- **Token:** a named design value, such as a colour or space value.
- **ADR:** architecture decision record, a short note that records a design decision.
- **ARIA:** attributes that help assistive tech when native HTML is not enough.
- **Functional pattern versus perceptual pattern:** what a thing does versus how it feels.

This is new for most people. Go slowly.

### Group 1 - Component API and first builds

#### Task - Component inventory and API design (ID `T2.1`)

##### 1. What We Are Doing
Pick six components to own this sprint. Design each API before you draw anything.

##### 2. Why We Are Doing It
The API is the contract. If you design it first, you prevent unplanned extra work and make defaults that help people use the system well.

##### 3. What to Learn First
A useful split is functional patterns, what a thing does, and perceptual patterns, how a thing feels. Two components that look different but do the same job are a duplication problem. Two that look the same but do different jobs are a naming problem.

##### 4. Where to Find Resources
Atomic Design, atoms, molecules, organisms chapters. Design Systems, Kholmatova, Ch. 4-5. Your Sprint 1-3 components.

##### 5. Step-by-Step Guide
1. Pick six components. At least one must be complex: a data table, a combobox, a date picker, or a multi-select.
2. For each component, write the variants. Say what fundamentally different versions exist.
3. Write the sizes. Say how many, and why that many.
4. Write the full set of states.
5. Write the slots. Say where a consumer can put arbitrary content.
6. Write every prop, with its default.
7. For every property, answer three questions: why does it exist, what happens if it is absent, what does it prevent someone from doing?
8. Then write what the component does not do, and where that responsibility lives instead.
9. Fill in the blank button API template below with your own answers.
10. Save the file at `students/UX{n}/week14/T2-1-component-apis.md`.

Blank template, a button API. Fill every line from your own project and justify each choice. Do not copy a published system.

> **Variants:** list your variants. For each one, say which hierarchy or job it serves. Say why the number is this number. If two variants do the same job with a different look, merge them and write why.
>
> **Sizes:** list your sizes with pixel values. Say why each size exists, which screen or context needs it, and which size is the default.
>
> **States:** list every state your component must support. Say why each one is needed.
>
> **Slots:** list your slots. For each slot, say what may go in it. Say which parts are props instead of slots, and why.
>
> **Props:** list every prop with its type and its default.
>
> **Default for `variant`:** state your default and defend it. Why is this the safe choice for a full screen?
>
> **What this does not do:** name the jobs this component refuses, and name the component or pattern that owns each job instead. For a button, think about navigation versus action, and which element each one needs.

If you get stuck: read the Kholmatova section on functional and perceptual patterns again; search "component API design system"; ask in Discord with your draft and what you tried.

How to think about it: choose safe defaults, not loud defaults. Every prop is a promise you must support.

### Group 2 - Slots, documentation, composition

#### Task - Build three more, with slots (ID `T2.3`)

##### 1. What We Are Doing
Build the remaining three components, including your complex one. Use slots where content is genuinely arbitrary.

##### 2. Why We Are Doing It
Slots are powerful and dangerous. A slot with no rules lets someone put a form inside a table cell, and then your component is responsible for a layout you never designed.

##### 3. What to Learn First
Composition. Slot constraints. Empty and overflow behaviour.

##### 4. Where to Find Resources
Design Systems, the chapter on composition and system flexibility. Docs for Radix, React Aria, or Headless UI. Why headless libraries: they separate behaviour from appearance, the same separation you are making between API and visual design. They cannot fall back on visual defaults.

##### 5. Step-by-Step Guide
1. Build the remaining three components, including your complex one.
2. Use slots where content is genuinely arbitrary.
3. For every slot, state what is allowed in it.
4. For every slot, state what is not allowed in it.
5. Document what happens when a slot receives too much content.
6. Document what happens when a slot receives nothing.
7. Fill in the blank slot template below for each slot, with your own answers.
8. Copy a view-only link to the Week 14 page in your file.
9. Save the file at `students/UX{n}/week14/T2-3-components-2.md`, with the view-only Figma or Penpot link inside the note.

Blank template, one slot of one component. Fill it from your own component and justify each limit.

> **Slot name:** the name you give the slot.
>
> **Allowed:** what may go in this slot. Say why each item is allowed.
>
> **Not allowed:** what may never go in this slot. Say why, and say which component owns that job instead.
>
> **Empty behaviour:** what the component does when the slot receives nothing. Say why you chose that behaviour.
>
> **Overflow behaviour:** what the component does when the slot receives too much content. Say why you chose that behaviour.
>
> **Why these limits:** one short line on what would break in the design if this slot had no rules.

If you get stuck: reread the composition chapter; search "design system slots composition"; ask in Discord with the slot name and your allowed content list.

How to think about it: a slot without rules is not flexible. It is unclear.

### Group 3 - Accessibility and component ADR

#### Task - Accessibility specification (ID `T2.6`)

##### 1. What We Are Doing
Write an accessibility spec for each of your six components.

##### 2. Why We Are Doing It
Accessibility is part of the component API. If it is not specified, it will be inconsistent.

##### 3. What to Learn First
The first rule of ARIA applies. If a native element does the job, use it and add nothing. `<button>` beats `<div role="button" tabindex="0">` for all relevant accessibility needs, including the ones you have not thought of.

##### 4. Where to Find Resources
The ARIA Authoring Practices Guide pattern for each of your six component types, in full, including the keyboard interaction tables. WCAG quick reference: https://www.w3.org/WAI/WCAG22/quickref/

##### 5. Step-by-Step Guide
1. Read the ARIA APG pattern for each of your six component types.
2. Write the semantic HTML element for each component.
3. Write the ARIA role only if the native element is insufficient.
4. List every required attribute and its state changes.
5. Write the full keyboard interaction table for each component.
6. Write the screen reader announcement in each state.
7. Write the focus behaviour.
8. Write the target size. Meet 24×24 minimum, and note 44×44 where it applies.
9. Justify any ARIA use by the absence of a native equivalent.
10. Save the file at `students/UX{n}/week14/T2-6-a11y-spec.md`.

If you get stuck: read the APG pattern again; search "ARIA APG button combobox"; ask in Discord with the component and the state that is unclear.

##### 6. What to Commit

- [ ] Keyboard interaction table complete for each, matching the APG
