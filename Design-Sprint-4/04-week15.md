## 1. What We Are Doing

This week you write the rules for your design system. You decide who owns it, who can change it, how a contribution is accepted or rejected, and how you remove something people already use. You also study what happens when someone bypasses the rules, and you revise your model after a governance failure.

The task groups are:

- Group 1 - Governance, contribution and rejection: G1.1, G1.2, G1.3
- Group 2 - Deprecation, versioning and critique: G1.4, G1.5, G1.6
- Group 3 - Governance failure: X4, P15.1
- Group 4 - Cohort day: S18.1, S18.2, S18.3, F15.1, F15.2, F15.3
- Group 5 - Code corner: Z15.1

## 2. Why We Are Doing It

A working product designer in India often joins a team where many screens, tokens and components already exist. The hard part is not drawing another button. The hard part is deciding which button is official, who can change it, and how to remove an old one without breaking other teams. This week gives you the language and documents for that work.

For your project, this week makes your system usable by other people. For your portfolio, it shows that you can think beyond screens. A case study with a real contribution model, rejection message and deprecation plan is stronger than a case study with only final visuals.

## 3. What to Learn First

By the end of the week you can:

- Write a contribution model with stated rejection criteria
- Reject a contribution in a way the contributor accepts
- Deprecate something people are using, without breaking them
- Learn from a process failure and say which of your rules caused it

Core ideas to review first:

- A system needs one named owner, not a committee.
- Change rights differ by item: tokens, core components, patterns, docs, product-specific extensions.
- Approval cannot cover everything. Too much approval leads to bypass.
- A disagreement needs a real tiebreaker.
- An escalation path needs time limits at each stage.
- People will bypass a process. Your model needs a path back in.
- A contribution needs evidence, not just an idea.
- A rejection must offer an alternative and name what would change the answer.
- A deprecation needs a reason, a replacement, a migration path and a dated timeline.
- Semver (semantic versioning) is short. Read it in full.
- Visual change can be breaking in a design system.
- A post mortem names your rule that caused the failure, not only the person who bypassed it.
- Conway's law says systems mirror the communication structure of the organisation that builds them.
- CSS custom properties are a simple way to store tokens in code.

#### Task - Governance model (ID `G1.1`)

##### 1. What We Are Doing
Write a governance model with six sections. It says who owns the system, who can change what, how you resolve disagreement, how you escalate, and what happens when someone bypasses the process.

##### 2. Why We Are Doing It
A design system without clear decisions becomes a set of files that teams ignore. This document is the decision layer. It keeps the system alive when you are not in the room.

##### 3. What to Learn First
- The owner is a named role, not a committee.
- Change rights are a table, not a sentence.
- Approval must be limited.
- A tiebreaker is required.
- Escalation needs time limits.
- Bypass needs a path back in.
- A divergence register records exceptions.

##### 4. Where to Find Resources
- Design Systems, Kholmatova, Ch. 6-7.
- Polaris, Carbon and GOV.UK Design System contribution guides.
- GOV.UK component proposal process.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.1.
2. Write section 1: who owns the system. Use a named role.
3. Write section 2 as a table. Rows: tokens, core components, patterns, documentation, product-specific extensions. Columns: who can propose, who reviews, who decides.
4. Write section 3: what requires approval and what does not. Be generous. Say clearly what does not need approval.
5. Write section 4: how disagreements resolve. Give one real tiebreaker.
6. Write section 5: the escalation path. Add a time limit at each stage.
7. Write section 6: what happens when someone bypasses the process. Make it a path back in, not a punishment.
8. Write your own response to the first likely bypass. Do not copy an example.
9. In the response, name the three possible outcomes at review: it joins the system, it stays as a documented product-specific exception, or it migrates to the system component.
10. State the default outcome if nobody attends the review.
11. Add one sentence that justifies your response, in your own words.
12. Check your six sections against the Done when list.
13. Commit the file.

If you get stuck: read the GOV.UK proposal rule again. Search "design system governance contribution model". Ask in Discord with a screenshot of your change-rights table and say what is unclear.

How to think about it: this is not a punishment document. It is a record document. The default outcome should still be better than silence.

##### 6. What to Commit
- [ ] Path: `students/UX{n}/week15/G1-1-governance.md`
- [ ] All six sections
- [ ] The owner is a named role
- [ ] The change-rights table covers all five categories with all three columns
- [ ] There is a real tiebreaker
- [ ] Time limits at every escalation stage
- [ ] Section 6 provides a path back in rather than a punishment
- [ ] The response is your own, with a stated default outcome and a justification
- [ ] Commit message starts with the task ID: `G1.1 governance model`

#### Task - Contribution process (ID `G1.2`)

##### 1. What We Are Doing
Design the path from "I need something" to "it is in the system". Write a proposal template, review stages and a fast path.

##### 2. Why We Are Doing It
A process with unknown cost does not get used. People route around heavy paths. A clear process and a fast path keep contributions coming in.

##### 3. What to Learn First
- The proposal template asks for evidence, not just an idea.
- Review stages have named participants.
- Every stage states the time cost for the contributor and the reviewer.
- A fast path exists for small work.
- A documentation fix or a new icon should take minutes.

##### 4. Where to Find Resources
- A public RFC process, such as Rust's or React's RFC repository.
- Polaris contribution documentation.
- Your G1.1 model.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.2.
2. Write the full path from need to system.
3. Write the proposal template.
4. In the template, ask for the problem, and evidence that it is a real problem.
5. In the template, ask for what exists already and why it is insufficient.
6. In the template, ask for the proposed API. The API means how someone uses the component, including its options, states and behaviour.
7. In the template, ask for accessibility considerations.
8. List the review stages. Name who takes part in each.
9. Add time cost at each stage for the contributor and the reviewer.
10. Design the fast path. State which work qualifies.
11. Check the Done when list.
12. Commit the file.

If you get stuck: read the Polaris contribution docs again. Search "design system contribution process proposal template". Ask in Discord with your proposal template and one example.

How to think about it: the process should lower the cost of a good contribution. It should not only raise the cost of a bad one.

##### 6. What to Commit
- [ ] Path: `students/UX{n}/week15/G1-2-contribution.md`
- [ ] The full path documented end to end
- [ ] A proposal template that asks for evidence, not just an idea
- [ ] Review stages with named participants
- [ ] Time cost stated for every stage
- [ ] A fast path exists, with clear criteria for what qualifies
- [ ] Commit message starts with the task ID: `G1.2 contribution process`

#### Task - Rejection criteria (ID `G1.3`)

##### 1. What We Are Doing
Write the criteria for rejecting a contribution. Write the actual rejection message for each criterion.

##### 2. Why We Are Doing It
Being able to reject is what makes a system a system. A bad rejection costs you every future contribution from that person. A good rejection protects the system and keeps the person.

##### 3. What to Learn First
- Six or more criteria.
- Tone matters as much as the criterion.
- Every rejection offers an alternative.
- Every rejection names what would change the answer.
- A rejection can still take the reusable part and credit it.

##### 4. Where to Find Resources
- The rejected RFC you read on Day 2.
- Polaris contribution documentation.
- Your G1.1 and G1.2.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.3.
2. List at least six criteria. Include: it duplicates something that exists, it is too specific to one product, it has no evidence of need, it cannot be made accessible, it increases the API surface (the number of options and parts other people must support) more than it reduces work, and the maintenance cost exceeds the benefit.
3. Take the first criterion. Write the real rejection message in plain language.
4. In that message, offer at least one alternative.
5. In that message, name what would change the answer.
6. Under the message, write two sentences that justify your choice of tone.
7. Repeat steps 3 to 6 for each remaining criterion.
8. Read every message again. Remove any line that reads as dismissive.
9. Check the Done when list.
10. Commit the file.

If you get stuck: read a rejected RFC comment again. Search "design system contribution rejection criteria". Ask in Discord with one rejection message and ask, "Would you contribute again after this?"

How to think about it: a rejection is a design decision about a relationship. The answer is no to this proposal, not no to this person.

##### 6. What to Commit
- [ ] Path: `students/UX{n}/week15/G1-3-rejection.md`
- [ ] Six or more criteria
- [ ] A written rejection message for each
- [ ] Every message offers an alternative
- [ ] Every message names what would change the answer
- [ ] Each message has a short justification of your tone
- [ ] None of them reads as dismissive
- [ ] Commit message starts with the task ID: `G1.3 rejection criteria`

### Group 2 - Deprecation, versioning and critique

Learning notes for this group: save Day 3 notes in `students/UX{n}/week15/session3-learning.md` (commit message `week15 session3 learning notes`) and Day 4 notes in `students/UX{n}/week15/session4-learning.md` (commit message `week15 session4 learning notes`).

#### Task - Deprecate something real (ID `G1.4`)

##### 1. What We Are Doing
Pick something in the cohort's system that should not exist. Write the deprecation, record it, and help one peer migrate.

##### 2. Why We Are Doing It
Real systems carry old parts. If you cannot remove things, the system grows until nobody trusts it. A deprecation plan protects people who use the system while you remove the old part.

##### 3. What to Learn First
- Pick a real candidate: a duplicate, an over-specific component, a badly named token, or something from Sprint 1 that everyone has worked around.
- The deprecation has six sections: what and why, replacement, migration path, timeline, what breaks, who to talk to.
- The timeline has three dated stages.
- A peer migration will show problems you did not plan for.

##### 4. Where to Find Resources
- Carbon's deprecation policy.
- Material's deprecation policy.
- Any Angular or React deprecation policy.
- semver.org.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.4.
2. Pick one real item in the system.
3. Write what is being removed, in one sentence.
4. Write why it is being removed, in one sentence.
5. Write what replaces it.
6. Add a side-by-side comparison of the old item and the new one.
7. Write the migration path step by step.
8. Add an honest effort estimate for one team, in hours.
9. Write the timeline with three dated stages: marked deprecated, stops receiving fixes, removed.
10. Under the timeline, justify the length of each gap in one sentence, using your team's release rhythm.
11. Write what breaks if someone ignores this.
12. Write who to talk to if the migration does not work.
13. Record the deprecation in the system, using the Starter-safe workflow. Write the change to the tokens and the docs in `system/` as markdown, and put a view-only Figma or Penpot link in your note.
14. Change the shared library file only if the admin confirms you have library access. If it is not confirmed, do not wait: the `system/` files are the record.
15. Write the changelog entry.
16. Write the communication.
17. Post the communication in the cohort Discord channel.
18. Ask one peer to migrate their usage.
19. Log what went wrong in the peer migration.
20. Check the Done when list.
21. Commit the file.

If you get stuck: read one Carbon or Material deprecation notice again. Search "design system deprecation policy migration timeline". Ask in Discord with your timeline table and the peer migration problem.

How to think about it: the user of the old item is not your enemy. They have a release plan. Your job is to make the new path cheaper than the old one.

- [ ] All six sections
- [ ] The migration path is step by step, with an effort estimate
- [ ] The timeline has three dated stages with a justification for each gap
- [ ] Recorded in `system/` with a view-only Figma or Penpot link, plus a changelog entry
- [ ] One peer has migrated, and their problems are logged
- [ ] The communication is written and posted
- [ ] Commit message starts with the task ID: `G1.4 deprecate something real`

#### Task - Versioning policy (ID `G1.5`)

##### 1. What We Are Doing
Define what counts as major, minor and patch for a design system. Decide if a visual change is breaking. State how you communicate each type and your support window.

##### 2. Why We Are Doing It
Version numbers are a promise. In a design system, visual change is not caught by a type checker. You need a rule people can apply before they ship.

##### 3. What to Learn First
- Major, minor and patch mean different things in a design system.
- Visual change can be breaking.
- A colour change and a padding change can have different effects.
- Communication format differs by type.
- The previous major needs a support window.

##### 4. Where to Find Resources
- The changelog of a real design system for the last six months.
- semver.org.
- Your G1.4 deprecation work.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.5.
2. Define major, minor and patch for design system changes.
3. Answer the hard question: is a visual change breaking? Write your rule.
4. Test your rule against four effects: accessibility (contrast, target size), meaning (colour used for status or error), layout (size, position, spacing that moves other things), and interaction (states, focus, hit area).
5. If the rule misses one of the four effects, change the rule.
6. Write one sentence on why you changed it.
7. State how you communicate each type and where.
8. State your support window for the previous major.
9. Check the Done when list.
10. Commit the file.

If you get stuck: read the first page of semver.org again. Search "design system versioning visual breaking change". Ask in Discord with your visual change rule and one example.

How to think about it: the version number is for the person who has to upgrade, not for you. Write the rule they can use.

##### 6. What to Commit
- [ ] Path: `students/UX{n}/week15/G1-5-versioning.md`
- [ ] Major, minor and patch defined for design system changes specifically
- [ ] A stated rule for whether visual changes are breaking, with reasoning
- [ ] The rule checks accessibility, meaning, layout and interaction effects
- [ ] Communication channel and format stated per type
- [ ] A support window for the previous major
- [ ] Commit message starts with the task ID: `G1.5 versioning policy`

#### Task - Breaking change process (ID `G1.6`)

##### 1. What We Are Doing
Write the full process for shipping a breaking change. Cover the notice period, the migration guide requirement, automated migration, and teams who cannot migrate in the window.

##### 2. Why We Are Doing It
A team in a release freeze (a period when a team cannot release changes) cannot migrate. Your process needs an answer other than "too bad". This is the difference between a process people use and a process people fear.

##### 3. What to Learn First
- A breaking change needs a notice period.
- A migration guide is a requirement, not a nice extra.
- State if a codemod is expected. A codemod is an automated code-editing tool.
- State what happens to teams who cannot migrate in the window.
- The exception path must be written down.

##### 4. Where to Find Resources
- The real design system changelog you read on Day 4.
- Your G1.5 versioning policy.
- Your G1.4 deprecation timeline.

##### 5. Step-by-Step Guide
1. Open a new markdown file for G1.6.
2. Write the notice period for a breaking change.
3. Write the migration guide requirement.
4. State whether a codemod (an automated code-editing tool) or automated migration is expected.
5. Write the path for a team in a release freeze. Make it specific.
6. Write who approves an exception.
7. Write how long an exception lasts.
8. Check the Done when list.
9. Commit the file.

If you get stuck: read the changelog again and find one breaking change. Search "design system breaking change process migration guide". Ask in Discord with your exception path and one example team.

How to think about it: a process that has no exception path creates secret exceptions. Secret exceptions are harder to manage.

#### Task - Post mortem (ID `X4`)

##### 1. What We Are Doing
Write a post mortem for a governance failure in this sprint. The failure is a governance failure: something bypassed your process, your process blocked something legitimate, or a team has quietly forked half your components.

##### 2. Why We Are Doing It
A post mortem finds the rule that made the failure likely. If you only blame people, the rule stays and the failure returns.

##### 3. What to Learn First
- State the facts without blame.
- Name which of your governance rules caused it.
- "The team did not follow the process" is a symptom, not a cause.
- State the cost.
- Make one specific change to the model.
- Name one thing you deliberately do not change.

##### 4. Where to Find Resources
- The week 15 failure injection brief in the shared `fundamentals/` folder. File name `week15-failure-injection.md` (check the exact path in the repo before use).
- Your G1.1 governance model.
- Your G1.2 contribution process.

##### 5. Step-by-Step Guide
1. Open a new markdown file for X4.
2. Open the failure injection brief in `fundamentals/` (check the exact path in the repo before use).
3. Read it and note which rule of yours the injected situation tests.
4. If the brief is not in the repo, or no real failure happened this sprint, use the simulated incident option below.
5. If you used the option, write "Simulated incident" on the first line of your file.
6. Write what happened, factually.
7. Name which of your governance rules caused it.
8. Explain why not following the process was rational for them.
9. State what it cost.
10. Write what you change in the governance model, specifically.
11. Write what you deliberately do not change, and why.
12. Check the Done when list.
13. Commit the file.

> Simulated incident option. Use this only if no real failure happened. Write two or three sentences about a product team that skipped your process for a reason you can understand, for example a release deadline. Do not write the fix in this step. Label the top of your file "Simulated incident".

If you get stuck: read your G1.1 section 3 and section 5 again. Search "design system governance post mortem bypass". Ask in Discord with the rule you think caused it and one sentence on why.

How to think about it: step 10 matters. Reacting to every incident by adding a rule is how governance models become the thing everyone bypasses.

#### Task - Deprecation stage (ID `S18.2`)

##### 1. What We Are Doing
Check the deprecation from G1.4 against its timeline, and move it to its next stage only when that stage is due.

##### 2. Why We Are Doing It
A deprecation plan only works if the stages happen on their dates. Moving a stage early breaks people. Forgetting a stage makes the plan look fake.

##### 3. What to Learn First
- Check the dates in your G1.4 timeline.
- Move only the next stage, and only if it is due.
- Record the change in the system and the changelog.

##### 4. Where to Find Resources
- Your G1.4 deprecation file.

#### Task - CSS custom properties are tokens (ID `Z15.1`)

##### 1. What We Are Doing
Turn 5 of your design tokens into CSS custom properties in a plain CSS file. Use them on one component.

##### 2. Why We Are Doing It
Tokens in Figma are useful. Tokens in code are how developers use the same decisions. CSS custom properties are a simple bridge between design and code.

##### 3. What to Learn First
- A CSS custom property starts with `--`.
- You define it in `:root`.
- You use it with `var(--name)`.
- It is plain CSS, no framework.
- The token names should match your system, not a random demo.

##### 4. Where to Find Resources
- web.dev/learn/css
- MDN Styling_basics
- `../04-Tools-Setup.md` for VS Code setup on Mac and Windows.

##### 5. Step-by-Step Guide
1. Open VS Code. If VS Code is not installed, follow the VS Code setup in `../04-Tools-Setup.md` for Mac and Windows.
2. Create a new file named `z15-1-tokens.css`.
3. In `:root`, define exactly 5 custom properties from your system. Use names that match your tokens.
4. Write one component rule, for example `.button`.
5. Use all 5 tokens inside that component with `var(--name)`.
6. Optional: test the CSS in a local HTML file. Do not commit the HTML file.
7. Check the Done when list.
8. Commit the CSS file.

If you get stuck: read the web.dev/learn/css custom properties material again. Search "CSS custom properties var root". Ask in Discord with your CSS file and the line that is not working.

How to think about it: keep the names honest. If the token changes in the system, the CSS name should still make sense.

##### 6. What to Commit
- [ ] Path: `students/UX{n}/week15/z15-1-tokens.css`
- [ ] Exactly 5 custom properties are defined in `:root`
- [ ] The custom properties are real tokens from your system

- [ ] The file is plain CSS, no framework
