## 1. What We Are Doing

This week builds the token layer of your design system. You audit the cost of divergence, build primitive, semantic and component layers, theme three products, and document the tokens so the set can leave Figma as JSON and CSS later. You also migrate your old system and write down the limits of your architecture.

- Group 1 - Token architecture: T1.0, T1.1, T1.2, T1.3, T1.4, T1.5, T1.6, P13.1
- Group 2 - System: S16.1, S16.2, S16.3
- Group 3 - Fundamentals: F13.1, F13.2, F13.3
- Group 4 - Lab: L-PR3

## 2. Why We Are Doing It

In a working product designer job in India, you often support more than one product with a small team. If every screen hard-codes colours, spacing and states, each change becomes a hunt for values. Tokens let one decision change many screens and keep accessibility checks in one place. For your portfolio, this week shows systems thinking, handoff to engineers, and honest documentation, which hiring teams look for.

## 3. What to Learn First

By the end of the week you can:

- Build a three-layer token architecture and explain what each layer is for
- Name a token so that its name survives the value changing
- Theme three products from one token set without duplicating decisions
- Say what your token architecture cannot do

Core ideas to review first:

- A token has three layers: primitive, semantic, component.
- A primitive name describes the value, for example `blue-500`. A semantic name describes the job, for example `interactive-default`.
- Components consume semantic tokens. Components do not use primitives directly.
- Theming means re-pointing semantic tokens to different primitives. It does not mean redesigning components.
- Density is a scale swap. It is not a second component.
- Dark mode is not inversion. Re-measure contrast.
- A token set must be written down so it can leave Figma later. Figma variables alone cannot be used outside Figma. This week you document the set in markdown. CSS and a real export come in week 15.
- Every architecture has limits. Write them down in the ADR. ADR means architecture decision record, a short document that records one decision and its reasons.

#### Task - Audit and divergence cost (ID `T1.0`)

##### 1. What We Are Doing
List every divergence in the brief audit and cost each one. Decide what a token layer will fix and what it cannot fix.

##### 2. Why We Are Doing It
You need a reason to build tokens beyond "systems are good". Cost and risk show where tokens help and where a component problem is hiding.

##### 3. What to Learn First
- Design Systems ch. 1 to 3, on what a system is for.
- `01-project-brief.md`, sections 2 and 4.

##### 4. Where to Find Resources
- Design Systems, Kholmatova, ch. 1 to 3.
- `01-project-brief.md`, sections 2 and 4.
- `06-token-architecture.md`.

##### 5. Step-by-Step Guide
1. List every divergence in the brief audit: the six buttons, four date pickers, three "urgent" colours, nineteen greys, and the amber-versus-grey "awaiting review" status.
2. Classify each one: accidental (nobody decided), necessary (the products genuinely differ), or unknown (you would have to ask).
3. Cost each one in three kinds of cost: engineering hours duplicated per year, accessibility or regulatory exposure, and risk of a wrong clinical or patient decision.
4. Use estimates. Mark them as estimates. Say how you would find the real number.
5. Rank by total cost. The top item is rarely the one that annoys designers most.
6. Write what a token layer will fix, and what it cannot. Example: a date picker that fails keyboard access is a component problem, not a token problem.

Worked example, a different company, one row:

> Three error reds (accidental). Engineering: about 6 hours a year per product keeping them in step. Exposure: low-vision users get inconsistent error signalling, a WCAG 1.4.1 risk. Clinical or financial risk: none. Total rank: 7 of 12. A semantic token makes error colours consistent; separately check that errors include a text or other non-colour indicator.
>
> Two checkout date pickers, one unusable by keyboard (accidental). Exposure: high, a keyboard-only user cannot complete a purchase. Rank 1 of 12. Tokens do not fix this, the component does.

How to think about it: cost is not only engineering time. A wrong patient status can be a safety event. If you cannot estimate, write the estimate you would use and the person you would ask.

If you get stuck: read the brief sections 2 and 4 again. Search for "design system divergence cost audit". Ask in Discord with your ranked list and what you tried.

#### Task - Primitive layer (ID `T1.1`)

##### 1. What We Are Doing
Build the raw values: colour ramps, type sizes, spacing, radii, border widths, shadows, durations and easings. Name them for what they are.

##### 2. Why We Are Doing It
Primitives are the bottom of the system. A stable primitive name lets the semantic layer change without renaming every value.

##### 3. What to Learn First
- `06-token-architecture.md`.
- Your T1.0 audit.

##### 4. Where to Find Resources
- `06-token-architecture.md`.
- Your T1.0 audit file.

##### 5. Step-by-Step Guide
1. Build the raw values for colour, type, spacing, radii, border widths, shadows, durations and easings.
2. Name primitives for what they are, never for what they do. Examples: `blue-500`, `space-4`, `radius-md`, `duration-200`.
3. Colour: make full ramps, 50 to 900, perceptually even, for every hue you need. Include a brand hue, a neutral, and one each for success, warning, error and information.
4. Check that nothing in this layer references anything else. Primitives are the bottom.
5. Write the rule: no component references a primitive directly.

Worked example, the naming rule tested:

> `blue-500` is a valid primitive name because it describes the value. If the brand changes to green, this token does not get renamed. It gets removed, and a `green-500` takes over the semantic slots it was filling.
>
> `primary-blue` is an invalid primitive name, because it mixes a role ("primary") with a value ("blue"). The moment primary becomes green, the name is a lie and every usage has to be found by hand.

If you get stuck: read the "Format" section of `06-token-architecture.md` again. Search for "design token primitive naming". Ask in Discord with one ramp and your naming rule.

#### Task - Semantic layer (ID `T1.2`)

##### 1. What We Are Doing
Create semantic tokens that name a role and point at one primitive. Components consume this layer.

##### 2. Why We Are Doing It
This is the layer that makes theming possible. If a semantic token is named for its job, the value can change without a rename.

##### 3. What to Learn First
- Shopify Polaris tokens documentation.
- IBM Carbon colour tokens and theming model.
- Adobe Spectrum tokens section.
- `06-token-architecture.md`.

##### 4. Where to Find Resources
- Shopify Polaris tokens documentation.
- IBM Carbon colour token documentation.
- Adobe Spectrum tokens section.
- `06-token-architecture.md`.

##### 5. Step-by-Step Guide
1. Give every semantic token a role and point it at exactly one primitive.
2. Cover text: default, subdued, disabled, on-colour, link, error.
3. Cover surface: default, raised, sunken, overlay, disabled.
4. Cover border: default, subdued, focus, error.
5. Cover interactive: default, hover, pressed, disabled, focus-ring.
6. Cover status: success, warning, error, info, each with a text, surface and border variant.
7. For every token, answer: what is this for, and when would I not use it?
8. Make sure components only consume semantic tokens. Components never touch primitives.
9. Measure every text-on-surface pairing. Record both resolved colour values and the measured ratio. All must meet 4.5:1.
10. Measure every border and focus ring. Record both resolved colour values and the measured ratio. All must meet 3:1.
11. Check that no component in your system references a primitive.

Worked example:

| Semantic token | Points at | Used for | Do not use for |
|---|---|---|---|
| `text-default` | `neutral-900` | Body copy, headings, labels | Text on a coloured surface. Use `text-on-colour` |
| `text-subdued` | `neutral-600` | Hint text, captions, timestamps | Anything a user needs to read to complete a task. On `surface-default` it may pass contrast, but it reads as secondary and users skip it. Write both resolved colour values and your measured ratio in your own table. |
| `border-focus` | `blue-600` | The focus ring, all components | Decorative borders. It must remain unique to focus or focus stops being recognisable. |

Note the third row: the constraint is not just contrast, it is meaning. A token whose visual language is borrowed elsewhere stops communicating.

If you get stuck: read your T1.1 primitives file again. Search for "semantic color token naming". Ask in Discord with one token row, both colour values and the contrast measurement.

#### Task - Component layer and theming (ID `T1.3`)

##### 1. What We Are Doing
Add component tokens only where a component genuinely needs to diverge. Theme the patient app, doctor console and admin portal by re-pointing semantic tokens and swapping density scales.

##### 2. Why We Are Doing It
Theming is the test of the architecture. If a theme needs a redesigned component, the architecture has a gap.

##### 3. What to Learn First
- Expressive Design Systems, Perez-Cruz, chapters on multi-brand and flexibility.
- Material 3 dynamic colour and theming.
- Your brief, re-read with theming in mind.

##### 4. Where to Find Resources
- Expressive Design Systems, Perez-Cruz.
- Material 3 dynamic colour and theming.
- Your brief.
- Your T1.2 semantic file.

##### 5. Step-by-Step Guide
1. Add component tokens as the third layer. Example: `button-primary-background` points at `interactive-default`, which points at `blue-600`.
2. Only create a component token where the component genuinely needs to diverge. Otherwise it consumes the semantic token directly. A component token for everything is not architecture, it is unnecessary extra work.
3. Open the brief and read it for one product at a time. Write one line per product: who uses it, where they use it, how much information they handle at once, and how much they have to read.
4. From those lines, decide what each product needs from a theme: colour tone, density, type size. Write each need as a difference in a token value, not as a new component.
5. Write one sentence of justification for each difference, with the sentence or section of the brief that supports it. If you cannot point at the brief, remove that difference.
6. Achieve every difference by swapping which primitive a semantic token points at, or by swapping a density scale.
7. If you find yourself redesigning a component to theme it, stop. Your architecture has failed. Log it.
8. Log every place theming was not enough, and say what you would restructure.

Worked example, density handled properly:

> The doctor console needs a compact table row. The wrong solution is a second table component. The right solution is a density scale: `space-comfortable-*` and `space-compact-*` primitive sets, with the semantic `table-row-padding` pointing at one or the other depending on the theme. The component is unchanged; the theme selects the spacing set.
>
> Where this broke for me: one product needs a button with a 32px radius, and my `radius-*` scale tops out at 12px. That is not a theming failure, it is a missing primitive. I added `radius-full`. The failure would have been overriding the radius inside the component.

How to think about it: theming is a test of your architecture. If a theme needs a new component, log it. Do not hide it.

If you get stuck: read T1.2 again. Search for "multi brand design tokens density scale". Ask in Discord with one theme difference and the token path.

#### Task - Naming audit (ID `T1.4`)

##### 1. What We Are Doing
Write your naming convention as a formal rule. Test every semantic and component token name against three questions, audit the primitives separately, and rename the ones that fail.

##### 2. Why We Are Doing It
A token name is a promise. If the name survives a value change, the system can change without a rename hunt.

##### 3. What to Learn First
- Your T1.2 semantic names.
- Naming conventions in Polaris, Carbon, Spectrum, and GOV.UK.

##### 4. Where to Find Resources
- Polaris, Carbon, Spectrum, and GOV.UK naming conventions.
- Your T1.2 file.

##### 5. Step-by-Step Guide
1. Write the convention as a formal pattern. Example: `{category}-{role}-{variant}-{state}`, or whatever you have chosen.
2. Verify every token conforms to the pattern.
3. Split your list in two: primitives in one list, semantic and component tokens in the other list.
4. Semantic and component tokens only: test each name. Does it survive the value changing?
5. Semantic and component tokens only: test each name. Can someone who has never seen your system guess what it does?
6. Semantic and component tokens only: test each name. Is it distinguishable from every other token when read quickly in a list?
7. Primitives, separate audit: does every primitive name describe only its value, with no role words? And does the scale follow one consistent pattern across every hue?
8. Find every token that fails its audit and rename it.
9. Write down the names you rejected and why. This stops the next person debating again.

How to think about it: a good token name is boring and stable. For semantic and component tokens, if the name mentions a colour, ask what happens when the brand changes. For primitives, the colour word is correct, so check the scale instead.

If you get stuck: read your T1.2 file out loud. Search for "design token naming convention". Ask in Discord with two names you cannot decide between.

#### Task - Dark mode (ID `T1.5`)

##### 1. What We Are Doing
Add a dark theme by re-pointing semantic tokens. Re-measure contrast and adjust elevation and saturated colours.

##### 2. Why We Are Doing It
Dark mode is a common product request. It is also a fast test of whether your semantic layer is doing its job.

##### 3. What to Learn First
- Your T1.2 semantic layer.
- Your T1.3 themes.
- `06-token-architecture.md`.

##### 4. Where to Find Resources
- Your T1.2 semantic file.
- Your T1.3 theming file.
- `06-token-architecture.md`.

##### 5. Step-by-Step Guide
1. Add a dark theme by re-pointing semantic tokens.
2. If you have to touch a component, note it as an architecture failure.
3. Do not invert. Pure black backgrounds with pure white text cause halation (a glow around light text on dark) and are uncomfortable.
4. Make elevated surfaces lighter in dark mode, not darker.
5. Desaturate saturated colours because they vibrate against dark backgrounds.
6. Re-measure every contrast pair. Record both resolved colour values and the measured ratio. Passing in light mode tells you nothing about dark mode.
7. Check all text-on-surface pairs pass 4.5:1.
8. Check all border and focus pairs pass 3:1.
9. State what you had to change beyond re-pointing, and why.

If you get stuck: read T1.2 again. Search for "dark mode design tokens contrast halation". Ask in Discord with one failing contrast pair, the two hex values and your measured ratio.

#### Task - Export (ID `T1.6`)

##### 1. What We Are Doing
Write the token set down in markdown so it can be exported: one table per theme, with the layer, the value and the alias for every token. Generating CSS and demonstrating the theme switch happen in week 15.

##### 2. Why We Are Doing It
A token set that exists only in Figma is not a token set. It is a set of Figma variables, and nothing outside Figma can use it. A written table with exact values is what an engineer needs, and it is the input for the JSON and CSS export later.

##### 3. What to Learn First
- Design Tokens Community Group 2025.10 format: the field names (`$type`, `$value`, aliases in curly braces) and the colour and dimension types.
- `06-token-architecture.md`, "Format" section.

##### 4. Where to Find Resources
- Design Tokens Community Group 2025.10 format specification.
- `06-token-architecture.md`, "Format" section.
- Optional reading only: Tokens Studio export documentation or the Style Dictionary build output guide. No install and no build this week.
- VS Code: see `../04-Tools-Setup.md`, VS Code section.

##### 5. Step-by-Step Guide
1. Create a markdown file `students/UX{n}/week13/T1-6-export.md`.
2. Write one table per theme, plus one table for dark mode.
3. Use these columns in every table: token name, layer (primitive, semantic, component), `$type`, value or alias, and a note.
4. Write aliases in the standard style with curly braces, for example `{color.blue.600}`.
5. Write colour values in a structured form, for example the hex value plus the colour space. Write dimension values with a unit, for example `16px`.
6. Check that every semantic and component token in your table points at a token that also appears in the same table.
7. Add a short section "How to turn this table into JSON": the fields, the order, and the steps. Do not run a build tool this week.
8. Add a short section "What comes in week 15": generating CSS custom properties for at least two themes, one selector per theme on the root element (for example `[data-theme="light"]` and `[data-theme="dark"]`), and then the theme switch demo with no component edits.
9. Add one line saying where the shared JSON lives: `system/`, not your student folder. Agree in Discord who writes it.

If you get stuck: read the "Format" section of `06-token-architecture.md` again. Search for "Design Tokens Community Group format JSON example". Ask in Discord with one table row and what you are unsure about.
